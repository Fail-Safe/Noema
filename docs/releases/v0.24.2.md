# Noema v0.24.2

This patch fixes federation catch-up, purge replay, background-work
ownership, and consolidation election when a peer goes offline. It also
quiets successful installer output. Event payloads and the divergence body
format are unchanged.

## Federation catch-up

A cortex joining a ring could stall while replaying a peer's history. A
second same-day divergence on one trace reused that day's note id, the
insert failed, and the cursor never advanced. Opening the joiner could also
purge another cortex's historical trash and publish those purges.

- Catch-up stores the remote event and materializes the divergence note the
  participants already wrote. It records a new note only when this cortex
  authored the snapshot that is applied.
- The note and the remote event commit together. If that note is already
  present, replay stores the missing event.
- The first live note of the day still uses the `YYYYMMDD-slug` id. Another
  note for the same trace that day appends a stable suffix derived from the
  two event ids.
- Automatic trash expiry skips trash authored by another cortex before this
  cortex existed. Local expiry is unchanged, and a peer's own purge event
  still replicates.

A joiner already stuck on v0.24.1 can resume on this build. A note left by
the failed attempt is kept. A peer that remains on v0.24.1 can still stall
on a second same-day live conflict; that peer needs this build.

## Purged traces

Catch-up applied `create` before `purge`, and `replay_purge` removed only
`trash/traces/<id>.md`. An active or archived copy could remain on disk with
no database row. With the watcher running, that file was ingested as a new
local create.

`replay_purge` now deletes whichever of `traces/`, `archive/traces/`, or
`trash/traces/` holds the file, in the same transaction as the row delete.
The watcher and `noema sync` refuse a file whose id is a purge tombstone:
they delete the file and do not author an event. A later live row for that
id is left alone.

## One background worker per cortex

Federation polling, the file watcher, trash expiry, consolidation, and
embedding maintenance now share `.noema-background.lock` in the cortex
directory. Separate runtime directories no longer elect a second owner.
`flock` releases the lock when the owner exits or is killed. A PID in the
file is diagnostic only.

HTTP `noema serve` and stdio MCP use the same lock. The first process to
acquire it runs background work. A later process still serves MCP and logs
`another process owns cortex background work; serving MCP only`. It does not
take over while it keeps running. After the owner exits, the next process to
start acquires the lock. Start the HTTP server first when it should poll.

This build also holds the v0.24 runtime-directory lock when that directory
is writable, so a v0.24 process in the same runtime directory still yields or
wins as before. A v0.24 process using a different runtime directory cannot
see the cortex lock. Upgrade the local servers for a cortex together.

## Consolidation election

Fixes [#262](https://github.com/Fail-Safe/Noema/issues/262). A peer that
stopped refreshing its rank kept that rank forever. When it was the highest,
every online node deferred and the pass was skipped. Turning consolidation
off also left the previous rank in place.

- A rank can win only while it is at least one quiet period old (twice the
  federation interval) and no older than that quiet period plus 30 minutes.
  One missed 15-minute refresh still counts. A peer that stays silent longer
  is ignored, so an online peer can win.
- When a consolidation block is configured, a node that is disabled, has no
  cron, idle, or threshold trigger, is in subscribe mode, or has the model
  disabled advertises rank 0 before it accepts traffic.
- The cron day is remembered only in the running process. A start after the
  scheduled time runs that day's pass, and a later restart the same day
  catches up again.

## Installer

On a successful install, `noema version` prints once, after `Installed:`.
macOS `codesign` output is shown only when signing fails. A failed
compatibility check is reported on stderr and the existing install is left
in place.

## Upgrade

```sh
brew update
brew upgrade noema
```

Alternatively, use the installer, download the matching platform archive and
verify it against `checksums.txt`, or build from the v0.24.2 source tag.
Restart Noema servers and stdio MCP clients after upgrading so they use the
new executable.

No Cortex data or configuration migration is required. No plugin or
dependency updates are included.

## Verification

Formatting, strict Clippy, the full Rust suite, and continuity harness
mechanics are covered by `make test`. Hosted pull-request CI is the merge
gate for this promotion. Publishing the tag builds and smoke-tests the
platform archives; it does not install or restart resident services.
